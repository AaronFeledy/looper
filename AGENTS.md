# AGENTS.md

This file is for non-obvious repo context only. Keep it short and current.

## Stack

- Bun + TypeScript, no bundler. `tsc -b` typecheck only, `noEmit: true`.
- Runtime deps: `@opentui/core`, `@opencode-ai/sdk`, `yaml`. No other production deps; do not add them lightly.

## Commands

- `bun install`
- `bun run typecheck`
- `bun test` &mdash; includes a real-network e2e against opencode + gpt-5.5; self-skips when `opencode` is not on `PATH`. ~50 seconds, ~zero cost.

## Architecture

- `src/main.ts` &mdash; CLI entry. Decides TTY vs non-TTY mode, owns the renderer, spawns/attaches the opencode server, and wires `src/engine/run-engine.ts`.
- `src/engine/run-iteration.ts` &mdash; runs one iteration: loop over steps, handle restart / skip / failure retries / background-task waits. `src/lib/orchestrator.ts` is a compat re-export shim. `runIteration` accepts an optional `resume` (`{sessionID?, messageID?, stepName?, promptText?, looperMessageIDs?}`) applied to the first processed step: if the recorded session is still `pending` and a `messageID` exists it reattaches via `reattachOpenCodeStep`; `messageID` selects the user turn whose assistant result determines the outcome, while `looperMessageIDs` independently identifies Looper-authored user turns hidden from output. A verified `idle` session normally restarts the step fresh, but an explicit manual recovery-nudge reuses that idle failed session, sends only a short continue-working turn, and retains the matching step row so its output and `startedAt` survive; `run-engine.ts` reuses the same iteration state for that recovery hop and skips iteration-start reset hooks. If the row no longer matches the configured step it is rebuilt safely, and if no session can be reused the nudge degrades to a normal fresh restart with the full original prompt. For any other state (`unknown`, `pending`-without-`messageID`, or a step-name mismatch) it fails CLOSED &mdash; `stopServerSession` must confirm the old session is stopped before a fresh one is created, never proceeding on an unconfirmed stop (matches the no-overlapping-generations guard).
- `src/lib/prompt-context.ts` &mdash; pure builder for the `<looper-context>` block prepended to every step prompt. `src/engine/run-iteration.ts` composes it fresh immediately before each `runOpenCodeStep` call (the single prompt-send call site, so fresh/nudge/restart/retry/background-continuation prompts all get it for free) using a dedicated `completedLogicalSteps` ledger keyed by `stepIndex` &mdash; never `state.steps` rows and never the pre-existing `completed` array &mdash; so duplicate step names stay distinct entries and the current step's own retry/restart attempts never appear as a "prior step" of itself. A gate-skipped step is deliberately excluded from this ledger (see the `step-gate.ts` note below), so it never appears as a "prior step" either. Agents never see past-iteration data (the "iteration N of M" counter is the only trace of the past). The ledger is seeded on resume from `RunState.stepSessions` (see the `run-state-store.ts` note below), filtered to `stepIndex < startStepIndex` so an in-flight step's own orphaned session can't leak into its own first prompt after a crash/resume. `context:` policy (see `config.ts`'s `resolveContextPolicy`) is resolved per step and can disable any of the eight sections, including `story` (branch/storyId/passes/phase; omitted entirely when no branch is derivable, and per-field within the block when a given fact is unknown). The `prd` section uses `derivePrdPaths` once per iteration to expose `prd.dir`/`prd.index`/`prd.progress` (repo-relative inside `repoDir`, absolute outside) plus fresh counts when readable; the same derived values feed gate-script environment variables, and no progress file is created. The `ContextPolicy` type (`prompt-context.ts`), `CONTEXT_KEYS` array, and `DEFAULT_CONTEXT_POLICY` (both `config.ts`) are three hand-synced lists of the same key set; `test/prompt-context.test.ts` asserts `CONTEXT_KEYS.length === Object.keys(DEFAULT_CONTEXT_POLICY).length` as a drift guard, but a new key still needs manual edits in all three places plus `buildLooperContext`.
- `src/lib/story-id.ts` &mdash; `storyIdFromBranch(branch, pattern?)` (default `^([a-z]+-[0-9]+)-`, capture group 1 uppercased; an invalid user regex is treated as no-match, never throws) and `currentGitBranch(repoDir)` (`git rev-parse --abbrev-ref HEAD`, ~2s timeout, `undefined` on any failure including detached HEAD's literal `"HEAD"`). Never reads `state.branch` or the branch watcher; every gate/context/signal caller re-derives the branch fresh from git, once per use, rather than trusting cached UI state.
- `src/lib/story-state-files.ts` / `src/persistence/story-state-store.ts` &mdash; `.looper-story-state.json`: `{ stories: { [storyId]: { phase: StoryPhase, updatedAt } } }`. `StoryPhase` is the ordered `STORY_PHASE_ORDER` (`building < implemented < reviewed < verified < published < merged`), compared via `comparePhase`. Tolerant parse (malformed file or any malformed entry collapses the whole read to an empty map, never throws); writes are read-modify-write via the existing `writeFileAtomically`. `clearStoryState()` runs on `--fresh` only, at all three `--fresh` clearing sites (TTY startup, TTY mid-run restart, and the non-TTY `fallback.ts` path) &mdash; never on normal run-end cleanup, since per-story keying makes a stale entry for an unrelated branch/story harmless.
- `src/engine/step-gate.ts` &mdash; pure `evaluateGate(inputs)`: `gate.branch: "story"` needs a derivable story id, `"main"` needs the current branch to literally be `"main"`; `gate.prdPasses` needs `passes === true` for that story (missing story id, missing prd config, or unreadable `prd.json` all fail); `gate.phase` needs `comparePhase(currentPhase ?? "building", gate.phase) >= 0`; `gate.script` needs a script that ran and exited 0. All configured conditions are AND-combined; the failure reason names the specific failing condition. `runGateScript` spawns `bash -c <script>` as a detached process group with `LOOPER_BRANCH`/`LOOPER_STORY_ID`, `LOOPER_PRD_DIR`/`LOOPER_PRD_INDEX`/`LOOPER_PRD_PROGRESS`, and `LOOPER_LAST_ADJUDICATED_AT`/`LOOPER_ADJUDICATION_COUNT` (from the adjudication completion log; `""`/`"0"` when none) overlaid on the inherited process env (empty string when unavailable); on timeout (`LOOPER_GATE_SCRIPT_TIMEOUT_MS`, default 30000) it SIGTERMs then SIGKILLs the whole group so a timed-out script can't keep mutating the repo after looper has already moved on. In `run-iteration.ts` a failed gate produces a distinct `completionKind: "gate-skip"` (vs `"done"`/`"runtime-skip"`); `run-engine-step-hooks.ts` advances the resume pointer for `done` AND `gate-skip` alike (ordinary manual/interruption skips do not advance), but a gate-skip is excluded from the `completedLogicalSteps` prior-steps ledger.
- `src/core/step-attempt.ts` &mdash; `StepAttemptState` groups the per-step mutable retry/reattach/resume-nudge fields `runIteration` used to hold as loose local vars, plus pure decision functions (`decideAfterFailurePolicy`, `decideAfterPriorEvaluation`, `decideAfterPriorHealth`) called only after their IO has completed, composing (never duplicating) `retry-policy.ts`/`resume-policy.ts`. `test/step-attempt-characterization.test.ts` locks every fail-path outcome (result status, row state, exact log lines) as a refactor guard for future `run-iteration.ts` changes to this area.  `run-iteration.ts` intentionally still takes a `LoopState` parameter for step-row ownership it hasn't been ported off yet (row splicing, `insertRestartAttempt`, and similar direct-array mutation); porting that onto the `StepReporter` ports above is a named follow-up, not an oversight.
- `src/core/step-view.ts` / `src/core/pending-request.ts` &mdash; neutral types (`StepStatus`, `StepRowView`, `TodoItem`, `PendingRequest`, etc.) extracted out of `state.ts` so the port types in `step-reporter.ts` don't need to import `LoopState`; both are re-exported from `state.ts` for call-site compat.
- `src/persistence/state-file-operations.ts` &mdash; thin re-export facade (`stopFileExists`, `tolerantRm`) over `src/lib/state-files.ts`, so `src/opencode/*` can reach stop-file operations without importing `lib/state-files.ts` directly.
- `looper signal <kind>` subcommand (`src/lib/args.ts` command discriminant + `src/lib/signal.ts`) &mdash; `signal adjudicate --reason <text>` / `signal stop --reason <text>` / `signal stop-after-iteration --reason <text>` / `signal story-phase <phase> [--story <ID>]`. Resolves configDir the same way a normal run does and does not require a running looper process (cold-shell invocation is the point &mdash; it just writes the marker/stop-file/story-state files directly). Exit 0 on success; exit 2 with a usage message on an unknown kind, missing `--reason`, invalid phase, or an underivable story id with no `--story`. `story-phase` without `--story` derives the story id from the current git branch plus the config's `storyIdPattern`.
- Passes-vs-phase authority invariant: `passes` (read from `prd.json`) is authoritative for `gate.prdPasses` and for oscillation/adjudication detection; `phase` (`.looper-story-state.json`) is authoritative only for `gate.phase`. A `setsPhase` write is guarded twice: skipped (and the story auto-demoted to `building` instead) if that story's `passes` flipped true→false during the step, and skipped if it would regress the phase (monotonic &mdash; `setsPhase` never moves a phase backward; only auto-demote or `looper signal story-phase` do). The phase write/demote happens before `onStepFinish`/pointer advance, and a write failure fails the step closed rather than silently advancing past it.
- `src/opencode/*` &mdash; runs steps against opencode (`step-runner.ts`), reattaches/evaluates prior sessions (`reattach.ts`), supervises SSE event streams with watchdog/resubscribe/backfill (`event-stream.ts`), manages background continuation records (`background-tasks.ts`/`continuation-records.ts`), session health (`session-health.ts`), and opencode IDs (`opencode-id.ts`). `src/lib/runner.ts` is a compat re-export shim. Step rows are reported through the `StepReporter` port (see the `step-reporter.ts` note below), delivered as `RunStepContext` and built by `run-iteration.ts` via `loopStateRunStepContext`; `request-broker.ts` reads/writes pending permissions and questions through `PendingRequestPort` only, never `state.pendingRequests` directly. Every prompt is sent with a self-generated opencode `msg_…` id (see `createOpencodeID`) so failures can be correlated against the actual assistant message via `session.messages()`. The event subscription is supervised: a watchdog re-subscribes (and backfills missed output via `session.messages()`) when the SSE stream ends or stalls while `session.status` still reports the session busy &mdash; the prompt POST and the event stream are on separate `AbortController`s so reconnecting events never disturbs the in-flight prompt. An `empty` assistant classification (a turn that completed with no output/tool activity) is NOT believed immediately: `classifyAssistantWithReactivationGrace` (`assistant-classification.ts`) re-polls for `LOOPER_EMPTY_ASSISTANT_GRACE_MS` (default 10000, `0` disables) every `LOOPER_EMPTY_ASSISTANT_GRACE_POLL_MS` (default 500) before the verdict becomes a step failure &mdash; opencode itself auto-restarts a session that ends without assistant output, and looper's instant abort+retry used to race that revival. Any non-`empty` first verdict returns with zero extra requests, so a healthy step is never delayed. A session observed `pending` again during the window returns `in-progress` (deliberately a `failed` step result carrying a reactivation message, NEVER `done`) so the existing `evaluatePriorSession`/`reattachOpenCodeStep` path takes the session over while opencode is still generating; a re-classification that turned `done`/`failed` is returned as-is, while one that turned `in-progress` is ALSO treated as reactivation (a turn that already completed empty and is generating again is the revival, even before `session.status` catches up — believing the idle status there would complete the step while opencode keeps generating); a `session.status` probe that errors or is unknown is never read as reactivation and never ends the wait; `shouldStop` (quit/skip/restart/stop-file) exits instantly. Both empty→failure sites use it (`step-runner.ts` post-prompt, `reattach.ts` final classification) and nothing else &mdash; `evaluatePriorSession` deliberately has NO grace of its own, since adding one there would double the delay.
- `src/opencode/request-broker.ts` / `src/opencode/permission-audit.ts` &mdash; every Looper-issued permission/question decision is appended as redacted JSONL to configDir's mode-0600 `.looper-permission-log.jsonl`; patterns are never stored, write failures are diagnostic-only, and the log is never read for policy or auto-reply. It is cleared at all three `--fresh` paths (TTY startup, TTY mid-run reset, non-TTY fallback). Human gate keys are permissions `y/a/d/s`, questions `d/s`; `LOOPER_PERMISSION_GATE_MAX_MS` bounds an ask, `LOOPER_PERMISSION_TEARDOWN_MS` bounds teardown, and `LOOPER_PERMISSION_BELL` controls the TTY alert. An `always` reply is an OpenCode project-level side effect stored outside Looper's configDir and is **not** undone by `--fresh`.
- `src/lib/state.ts` &mdash; in-memory TUI state, listener pub/sub. The six control flags (`quitting`, `paused`, `skipRequested`, `restartRequested`, `restartReason`, `stopAfterIteration`) are now accessor properties that delegate to `state.control` (a `RunControl`, see the `run-control.ts` note below) for back-compat with existing `state.<flag>` call sites; new code should take `RunControl`/`RunControlView` directly instead of reading them off `LoopState`.
- `src/persistence/run-state-store.ts` &mdash; run-state write facade over `src/lib/state-files.ts` stop/resume files under the config dir. **Must call `initStatePaths({ configDir })` before state-files exports are used.** `.looper-resume-step.json` is the legacy step-only checkpoint (kept for back-compat); `.looper-run.json` (`RunState`: `{iteration, stepIndex, stepName, sessionID?, messageID?, promptText?, looperMessageIDs?, title?, looperRunID?, stepSessions?}`) is the authoritative iteration-aware resume pointer. `looperRunID` is generated per logical Looper run, persisted across resume, and sent in opencode session metadata for Looper-owned sessions. `sessionID`/`messageID`/`promptText`/`looperMessageIDs` are written only while a step is in flight (via `runOpenCodeStep`'s `onSessionBound`, fired right before `session.prompt`, or when OpenCode posts a continuation turn); `messageID` is the current outcome-classification turn, `promptText` is the exact Looper prompt shown by the prompt dialog, and `looperMessageIDs` is the ownership set used to hide only Looper-authored user turns. On step `done` the pointer is advanced to the next step (or next iteration) WITHOUT those in-flight fields, so `--continue` never reattaches to an already-completed step. Old files without prompt metadata remain valid and treat their in-flight `messageID` as the sole known Looper-owned ID. `title` is the iteration's generated work-description: it rides along with the pointer across step advances (so a resumed run rehydrates it into `runIteration`'s `initialWorkDescription` and steps that only inherit the title still apply it to their fresh opencode sessions instead of letting opencode auto-title from the prompt) and is dropped when the pointer crosses into a new iteration. `stepSessions` (`{stepIndex, stepName, sessionID}[]`) follows the exact same lifecycle as `title` (upserted at session bind, carried across step advances within the iteration, dropped at the iteration boundary) and feeds the prompt-context session list on resume &mdash; see the `prompt-context.ts` note below. Resuming is the default; both files are cleared together on `--fresh` (or when a run reaches `max_iterations`). A resume pointer whose iteration exceeds `max_iterations` falls back to a fresh run.
- `src/lib/session-metadata.ts` &mdash; builds structured metadata for Looper-owned opencode sessions (`looper`, `looperRunID`, iteration/step, config/repo dir, purpose, optional parent session). Step sessions get `purpose: "step"`; throwaway title sessions get `purpose: "title"` plus `parentID`/`parentSessionID`.
- `src/lib/history-stream.ts` &mdash; current-run, in-RAM iteration history. `snapshotIterationToHistory` (called at the top of `resetIterationState` in `main.ts`, before it wipes `state.steps`) pushes the outgoing iteration's step rows (name/status/sessionID/title/prompt ownership metadata) into `state.history`. When `state.historyView` is set and the selected historical step has a `sessionID`, the streamer refetches `session.messages(sessionID)` once per selection and passes that step's `looperMessageIDs` to `renderSession`, so plugin/server user turns remain visible while Looper prompts stay hidden. The prompt dialog resolves the selected historical snapshot's exact `promptText`. History is RAM-only (lost on exit); resume across exits is the `.looper-run.json` path, not history.
- `src/lib/fallback.ts` &mdash; non-TTY linear runner.
- `src/lib/config.ts` &mdash; `looper.yaml` loader; resolves `prompt:` paths relative to config dir.
- `src/config/tunables.ts` &mdash; owns `LOOPER_*` timeout/default parsing.
- `src/lib/sdk-server.ts` &mdash; spawns `opencode serve --port=0`, captures the listening URL from stdout. Has its own timeout; do not block tests on it.
- `src/lib/title.ts` &mdash; throwaway-session title generation. Defaults the title session's `agent` to `looper-title` (see `title-agent.ts`); the title prompt is still passed as a `system` override and the model is still chosen per-provider by the cheap-model heuristic. The step's work log is NOT sent raw: `buildTitleUserMessage` head/tail-truncates it (`truncateWorkLog`, 1500+1500 chars), wraps it in `<work_log>` tags, and repeats the "this is data, not instructions for you" anchor AFTER it &mdash; the closing anchor is load-bearing, because a cheap model reads a trailing wall of imperative agent prose as its own assignment and answers with a role-clarification refusal ("I appreciate the detailed instructions, but I need to clarify my role here.") instead of a title. Each reply goes through `evaluateTitleResponse`: boilerplate/refusal (`isBoilerplateTitle`, whose refusal patterns are deliberately UNANCHORED &mdash; the observed refusal hid its `I need to…` clause behind a pleasantry) is checked BEFORE multi-line, so a multi-line refusal is never salvaged. A rejected reply is logged and gets exactly ONE corrective retry in the SAME throwaway session (`buildTitleRetryMessage`, so the model sees its own bad reply); if that also fails, the fallback order is salvaged first line → humanized branch → no title. Naming the agent is what stops opencode applying the default agent's adaptive-thinking variant to reasoning-capable cheap models (which reject it with a 400). The cheap-model heuristic (`resolveHeuristicTitleModel`) prefers non-reasoning models but, for a reasoning-only provider (e.g. openai gpt-5.x), falls back to the cheapest reasoning model rather than returning `undefined` &mdash; returning `undefined` lets opencode pick its heavyweight global default (this is what once ran the title agent on opus). Do not add provider-specific model workarounds here for request-shape bugs; if a plugin injects invalid Anthropic thinking fields, fix that plugin so opencode/model metadata remains the source of truth. The whole create+prompt is bounded by `LOOPER_TITLE_GEN_TIMEOUT_MS` (default 60s); on timeout the title prompt is aborted so a misbehaving title agent can't run unbounded. The throwaway title session is ALWAYS aborted+deleted in the `finally` (success or failure) &mdash; an earlier "keep failed title session for review" path leaked sessions that each held a copy of the step work-log, and the failure is already logged, so it was rolled back.
- `src/lib/attached-server-agents.ts` &mdash; attach-mode preflight checks. In addition to managed agent validation, `assertAttachedServerLocation` best-effort checks the attached server's active location (prefer `client.v2.location.get`, fallback `client.path.get`) and fails early on repo-dir mismatch; if the SDK/server cannot report a location, attach behavior falls back to the managed-agent check.
- `src/lib/title-agent.ts` / `src/lib/opencode-managed-resources.ts` &mdash; materializes the hidden `looper-title` opencode subagent (`mode: subagent`, `hidden: true`, no `variant`) into opencode's GLOBAL agent dir. `main.ts` calls `ensureTitleAgent()` before the server starts. The agent frontmatter disables ALL tools (`tools: { "*": false }`) and denies tool permissions (`permission: { "*": deny, ... }`): it is fed a step's assistant work-log as its user message, and with tool access a capable model reads that as a task list and starts executing it (an observed opus runaway ran ~24 turns over 8 minutes). The disabled tools force a single text turn; `LOOPER_TITLE_GEN_TIMEOUT_MS` is the backstop for the `--attach` path where a running server may not have reloaded the locked-down agent file.
- `src/lib/event-consumer.ts` / `src/core/events.ts` / `src/presentation/legacy-line-format.ts` &mdash; event pipeline: SDK message/part events become the structured `LooperEvent` union, then golden-tested legacy text lines for terminal output.
- `src/engine/run-engine.ts` &mdash; shared loop for TTY and non-TTY frontends: resume plan, run-state advancement, stop handling, iteration invocation, and recovery retry selection.
- `src/engine/run-control.ts` &mdash; `RunControl`/`RunControlView` own the six run-control flags (`quitting`, `paused`, `skipRequested`, `restartRequested`, `restartReason`, `stopAfterIteration`) that used to live directly on `LoopState`. `createRunControl()` is created once per run, run-scoped rather than per-iteration: `main.ts` (TTY) and `fallback.ts` (non-TTY) each build one at startup and share it across the per-iteration `LoopState`s that follow. The `onChange` callback defaults to a no-op; `main.ts`'s existing explicit `notify()` calls after flag mutations were kept as-is, so TUI notify frequency is unchanged by this refactor. `RunControlView` (read-only flags plus `requestRestart`) is the surface handed down into `engine`/`opencode` code that needs to observe or request control state without the full mutable `RunControl`.
- `src/engine/step-reporter.ts` (re-exported from `engine-ports.ts`) &mdash; `StepLifecyclePort` (row transitions: begin/markWaiting/markWaitingForBackground/finalize/setSessionID/etc.), `StepOutputSink` (line/lines/event), and `PendingRequestPort` (permission/question queue) are aggregated into one `StepReporter`, threaded through the engine as `RunStepContext = { reporter, control }`. These ports exist so `src/opencode/*` can report step progress without depending on the TUI's `LoopState`: the rule is `src/opencode/*` may NEVER import `../lib/state.ts`, reference `LoopState`, or import `agent-tree-state.ts` &mdash; enforced by `test/architecture-guards.test.ts` (the boundary-enforcement tests are currently `describe.skip`'d pending full opencode/engine decoupling; only the regex self-tests run today, see the Gotchas note below).
- `src/lib/loop-state-reporter.ts` &mdash; the TTY `StepReporter` implementation: `createLoopStateStepReporter(state)` is a pure delegation adapter over existing `state.ts` helpers (`beginStepRun`, `finalizeStepRow`, `pushAgentLine`, etc.) plus `agent-tree-state.ts`'s `setStepContinuation`. Zero new logic lives here; `state.ts` stays the only place that actually mutates a `LoopStep`. `loopStateRunStepContext(state, control)` wraps it into a `RunStepContext`. Introduced two new `state.ts` helpers to back the port: `clearStepStatusMessageIf` (used to be an inline conditional clear in `opencode/reattach.ts`) and `markStepWaitingForBackground`, which differs from `markStepWaiting` in that it also clears `finishedAt` and `activeStepIndex` (so the row stops looking "active" while a background task runs) but deliberately does NOT clear `statusMessage` the way `markStepWaiting` does.
- `src/engine/headless-step-reporter.ts` &mdash; a reference non-TTY `StepReporter` implementation, `LoopState`-free, that doubles as the shared-contract test double (`test/helpers/step-reporter-contract.ts` runs the same behavioral contract against both this and `createLoopStateStepReporter`). Wiring it into `fallback.ts` at runtime is deliberately deferred: `fallback.ts` currently prints via the debounced module-level `notify()`/`subscribe` loop, and swapping in a reporter that writes/prints directly would reorder output relative to that debounce.
- `src/engine/stall-detector.ts` / `src/engine/stall-quiescence.ts` &mdash; cross-iteration circuit breaker for unbreakable loops where every step succeeds but the run advances nowhere. After each completed iteration the engine observes: HEAD, whether commits since the last observation touch any path outside the PRD dir (docs/progress churn is NOT progress), a worktree fingerprint of UNCOMMITTED material work, the PRD passes map, story phase, branch/story id, and the adjudication-completion count. The worktree fingerprint is a SHA-256 over the actual material working-tree CONTENT, never a summary: `git diff --name-only HEAD` and `git ls-files --others --exclude-standard` give the tracked/untracked dirty paths, each filtered through the SAME PRD-exclusion rule as commits (one `materialPaths` implementation) and sorted, then the tracked patch (`git diff --no-ext-diff --binary HEAD -- <trackedPaths>`, argv-safe, skipped when none, and the source of truth for DELETED tracked files &mdash; never passed to hash-object) and the untracked content hashes (`git hash-object --no-filters -- <untrackedPaths>`, skipped when none) are hashed together with the path lists; `""` = clean tree, `undefined` = any git command failed. Content hashing rather than `git diff --shortstat` is deliberate: a repo-wide shortstat moves on PRD churn that the material path list deliberately excludes (resetting the counter forever) while staying put on a same-line-count tracked edit or ANY untracked-file edit (missing real progress). The fingerprint is load-bearing, not a nicety: committed history alone cannot distinguish a story mid-implementation with uncommitted edits, or one whose commits land seconds after the iteration boundary, from a dead loop (an observed run halted with HEAD at main's tip while three commits and a story-phase advance landed 4-6 minutes later). PRD-only dirt collapses to `""` precisely so a per-iteration `progress.txt` write cannot reset the counter forever. A halt is gated in three layers: (1) any observed signal moving &mdash; including the worktree fingerprint &mdash; is progress and resets the counter; (2) a strike requires PROVEN quiescence &mdash; `stall-quiescence.ts` probes `probeBackgroundLiveness` over the step sessions the engine already tracks for the iteration plus `readActiveProjectContinuationRecord`, and while any parent/child session is pending, any continuation record is active, liveness is unknown, or the probe threw, the counter is HELD: neither incremented nor reset, AND the last proven-quiescent observation is kept as the comparison baseline (an in-flight sample is never written to `prev`, or the work done during it would be absorbed into the baseline and the next quiet iteration would compare dirty-against-dirty and score a strike for real progress). Holding rather than resetting is deliberate, so a wedged loop that always has a busy session can still trip on a later quiet iteration; (3) a stalled verdict is not acted on immediately &mdash; the engine waits a settle window (`LOOPER_STALL_CONFIRM_MS`, default 180000, `0` re-samples immediately rather than disabling; `stallConfirmMs` on the engine input for tests), polling so an arriving stop file or quit bails out the normal way instead of sleeping it out, then `confirmStall` re-samples EVERY signal the verdict was built from &mdash; branch, story id, HEAD, worktree fingerprint, liveness, story phase, PRD passes, adjudication-completion count, since passes/phase/adjudications can all advance during the window with no git change at all &mdash; WITHOUT mutating the detector's counters or `prev` (it is a second opinion, never a second strike). Any signal that moved, any unreadable fact, and a missing prior observation all fail open and refuse to confirm; only a still-stalled re-sample writes the stop file. K consecutive no-progress iterations (`stall.iterations` in `looper.yaml`, env `LOOPER_STALL_ITERATIONS`, default 3, 0 disables) or M completed adjudications attributed to one story within a run (`stall.adjudications`, env `LOOPER_STALL_ADJUDICATIONS`, default 3, 0 disables) writes the stop file with a diagnosis and stops the run. Fail-open everywhere: git failures, an unreadable worktree fingerprint, unknown baselines (first iteration, resume), a configured-but-unreadable PRD (folded into the quiescence gate rather than compared, because `passesEqual(undefined, undefined)` reads as "stable" &mdash; correct ONLY when no `prdDir` is configured; `confirmStall` likewise refuses while a configured passes map is unreadable on either side, and with no `prdDir` undefined-on-both-sides stays a valid stable state), unknown session liveness (tracked sessions with a client that cannot answer for them is UNKNOWN, not idle), and liveness-probe errors all count as progress, so a flaky environment can never stop a healthy run. Pure logic stays pure &mdash; `createStallDetector` does no I/O; all git and session probing lives in the observer and `stall-quiescence.ts`, and nothing new is probed when stall detection is disabled. In-memory per run &mdash; counters reset on restart; the durable stop file is the acknowledgement boundary.
- `src/engine/adjudication-routing.ts` / `src/persistence/adjudication-store.ts` / `src/lib/adjudication-files.ts` &mdash; PRD oscillation adjudication. State lives in `configDir` as `.looper-adjudicate` (marker + reason text), `.looper-prd-history.json` (per-story `passes` transition log plus an `adjudicatedThrough` watermark) , `.looper-adjudicate-session.json` (the in-flight adjudicator session) and `.looper-adjudication-log.json` (append-only `{at, reason}` records of COMPLETED adjudications &mdash; written just before the marker is cleared so the reason survives; exported to gate scripts as `LOOPER_LAST_ADJUDICATED_AT`/`LOOPER_ADJUDICATION_COUNT` so a gate can fire on deltas since the last adjudication instead of monotonic absolute thresholds that re-fire forever; cleared with history on `--fresh` only), owned by these files, NOT `state-files.ts` directly. `readPrdPasses` is per-story tolerant and semantically aligned with the canonical reader (`src/lib/prd.ts`): `passes === true` means passing, unusable stories (no id) are skipped rather than discarding the whole snapshot, so one malformed story can't silently disable detection. Detection runs only over the ACTIVE window (`readActiveHistory` = records after `adjudicatedThrough`): a story's `passes` flips true→false at least `prdFlipThreshold` times (`LOOPER_PRD_FLIP_THRESHOLD` env, else `prdFlipThreshold:` in `looper.yaml`, else default 2; resolved in `src/config/tunables.ts`). A completed adjudication calls `markAdjudicated` to advance the watermark, so resolved flips (and the adjudicator's own transitions) never retrigger while the full trail is retained for forensics. The optional top-level `adjudicate:` block in `looper.yaml` (same schema as one `steps:` entry, default name `adjudicate`, loaded by `loadAdjudicateStep` in `config.ts`; validated at startup by `ensureConfigValid` in `main.ts`) is never part of `loadSteps()`. Routing (`decideRouting` in `run-iteration.ts`, checked both mid-iteration and at iteration start so a stale/resumed marker routes before step 0): a detected or agent-written marker skips the remaining configured steps and runs the adjudicate step as one ephemeral dynamic row (`insertAdjudicationRow`) whose prompt is prefixed with the marker reason via `withAdjudicationReason`. The adjudicator's session is persisted (via `writeSession` in `onSessionBound`, before prompt dispatch) so a crash mid-adjudication is reconciled (confirm-stopped) at the next iteration-start routing before a fresh adjudicator launches &mdash; no overlapping generations. Only a `done` adjudicator clears the marker/session and advances the watermark; a non-`done` adjudicator FAILS CLOSED (marker retained for re-route, session confirm-stopped, `StepFailureError` thrown), never treated as resolved. No `adjudicate:` step configured: writes the stop file with the oscillation reason instead. The adjudicate row is never a resumable position (no run-state pointer entry); the marker + session record are the durable resume signals. `readPrdHistory` never overwrites a present-but-corrupt history: `appendPrdHistory` quarantines it to `.looper-prd-history.json.corrupt-<ts>` (or skips the write if it can't) rather than truncating forensic data. History/session clear only on `--fresh`, never via `clearRunArtifacts` (survive normal run-end cleanup).
- `src/watchers/*` &mdash; branch/GitHub/PRD watchers and branch-delta helpers.
- `src/tui/*` &mdash; opentui renderables. TUI output blocks are built from structured events via `src/presentation/tui/stream-blocks.ts`; the contract is the `LooperEvent` union plus the golden-tested legacy formatter, not a string parser.

## Gotchas

- Path semantics: `repoDir = process.cwd()`. `configDir` is resolved (in `main.ts`) from `--config-dir`, else `LOOPER_CONFIG_DIR`, else the first of `$PWD/.looper`, `$PWD/.local/looper`, `$PWD/.local/.looper` that already holds a config file, else defaults to `$PWD/.looper`. State files live in `configDir`. The CLI auto-creates `configDir` but fails with exit 2 if no config file is present. Config file resolution prefers `looper.yml`, then `looper.yaml`, `.looper.yml`, `.looper.yaml` (see `CONFIG_FILE_NAMES`/`findConfigFile` in `config.ts`).
- `bin/looper` is a bash wrapper that resolves symlinks itself; symlink it from `~/.local/bin/looper` and it still finds `src/main.ts`.
- `noUncheckedIndexedAccess: true` is on. `frames[i]` from a literal array still needs `!`.
- `src/opencode/background-tasks.ts`'s `LOOPER_CONTINUATION_EXIT_GRACE_MS` window decides how long to wait after an opencode step ends for a background-task record. Don't shorten it in tests unless you mock the file.
- `event-consumer.ts` debug logs gate on `LOOPER_DEBUG_EVENTS=1`.
- `LOOPER_EMPTY_ASSISTANT_GRACE_MS` (default 10000, `0` disables) / `LOOPER_EMPTY_ASSISTANT_GRACE_POLL_MS` (default 500) bound the empty-assistant reactivation wait; see the `src/opencode/*` note above. Tests that assert the empty→failure path must shrink them (the wait is real time), as `test/runner-reconnect.test.ts` and `test/step-attempt-characterization.test.ts` do in their `beforeEach`.
- `ensureTitleAgent()` (`title-agent.ts`) writes `looper-title.md` into opencode's GLOBAL agent dir (`$XDG_CONFIG_HOME/opencode/agent`, else `~/.config/opencode/agent`) at startup &mdash; a side effect outside `configDir`/`repoDir`. It only overwrites a file carrying its own managed marker, never a user-authored `looper-title.md`. Caveat: it's written before looper *spawns* opencode, so the spawn path picks it up at boot; on the `--attach`/`attachUrl` path the already-running server may not have loaded it, in which case title gen degrades to no-title (best-effort) rather than breaking the loop.
- `LOOPER_GATE_SCRIPT_TIMEOUT_MS` (default 30000, `src/config/tunables.ts`) bounds a step's `gate.script`; see the `step-gate.ts` note above.
- `src/opencode/event-stream.ts`'s event watchdog is tunable via `LOOPER_EVENT_WATCHDOG_POLL_MS` (default 15s), `LOOPER_EVENT_STALL_MS` (default 45s; how long no events may pass before it probes `session.status`), and `LOOPER_EVENT_RESUBSCRIBE_BACKOFF_MS` (default 1s floor between reconnects). A stream that ends cleanly triggers an immediate probe regardless of the stall window. `createSessionEventConsumer` keeps print/dedup state across reconnects so resubscribe + `backfill()` never double-prints.
- The e2e test uses `agent: build` + `model: openai/gpt-5.5` + `variant: low`. Reasoning-only models (e.g. claude-haiku-4-5) reject the build agent's adaptive-thinking variant with a 400 &mdash; if you change the model, also align the agent/variant.
- Test scratch dirs land under `test/.tmp/` and are auto-cleaned unless `LOOPER_E2E_KEEP=1`.
- `test/architecture-guards.test.ts` is the executable boundary enforcement for "`src/opencode/*` must not depend on `LoopState`": an unexpected import of `lib/state.ts` (or a control-flag read) from `src/opencode`/`src/engine` fails that test, not just code review.
